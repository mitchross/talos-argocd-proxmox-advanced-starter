# stateful-demo — `backup: hourly` PVC label pattern

The headline feature of this starter: **add one label to a PVC, and
the platform handles backup, retention, and restore**. No per-app
backup configuration, no manual VolSync resources, no shell scripts.

This demo is a single PVC carrying `backup: hourly` plus a tiny
busybox Deployment that writes a timestamp every 30 seconds. The
point isn't the workload — it's watching pvc-plumber wire up backup
plumbing automatically.

> **Pre-requisite**: the Kopia password SealedSecret at
> `infrastructure/controllers/pvc-plumber/sealed-kopia-password.yaml`
> must be sealed via `scripts/seal-secret.sh` BEFORE this demo first
> reconciles. Without it, the per-PVC `ExternalSecret` ESO templates
> from the master `1password` ClusterSecretStore won't have a value
> to copy, and the VolSync mover Job can't open the Kopia repository.
> See `docs/getting-started.md` for the recommended pre-sync ordering.

---

## What pvc-plumber does for you

Within a few seconds of ArgoCD applying `pvc.yaml`:

```bash
kubectl get externalsecret,replicationsource,replicationdestination \
  -n stateful-demo -l volsync.backup/pvc=stateful-demo-data
```

Expected output:

```
NAME                                                         STORE       REFRESH INTERVAL  STATUS  READY
externalsecret.external-secrets.io/volsync-stateful-demo-data  1password  1h                SecretSynced   True

NAME                                                                          SOURCE                LAST SYNC                AGE
replicationsource.volsync.backube/stateful-demo-data-backup                   stateful-demo-data    -                        15s

NAME                                                                          LATEST IMAGE
replicationdestination.volsync.backube/stateful-demo-data-backup
```

All three resources were generated by the operator's PVC reconciler
when it saw the `backup: hourly` label. None of them are checked into
git; they're spec'd entirely from the label.

The `ReplicationSource` won't run its first backup until two
conditions are met:

1. The PVC is `Bound` (immediate after the Deployment claims it)
2. The PVC has been bound for **2 hours** (deliberate delay — see
   below)

The 2-hour wait is intentional. Without it, a freshly-restored PVC
that's still empty would have a backup snapshot taken of its empty
state, which would then become the "latest backup" and overwrite the
real data on the next restore-from-empty cycle. Two hours is a safe
margin for any restore process to finish.

For impatient verification, you can drop the wait by bumping the PVC's
`creationTimestamp` artificially or by triggering a manual backup —
see "Triggering a manual backup" below.

## Verifying data is being backed up

### Step 1 — see real data flowing

```bash
kubectl exec -it -n stateful-demo deploy/stateful-demo -- tail -f /data/heartbeat.log
```

You should see a new line every 30 seconds.

### Step 2 — wait for the first scheduled backup

The schedule is computed deterministically:
`sha256("stateful-demo/stateful-demo-data") % 60` minutes past the
hour. Find it:

```bash
kubectl get replicationsource -n stateful-demo stateful-demo-data-backup \
  -o jsonpath='{.spec.trigger.schedule}'
# example output: "23 * * * *"
```

After the next tick + 2-hour grace, watch:

```bash
kubectl get replicationsource -n stateful-demo stateful-demo-data-backup -w
# expected: lastSyncTime field populates with a timestamp
```

### Step 3 — verify the backup landed in the Kopia repository

```bash
kubectl exec -n volsync-system deploy/pvc-plumber -- kopia snapshot list \
  /repository \
  --filter "ns=stateful-demo,pvc=stateful-demo-data"
```

You should see one snapshot per scheduled tick, each with a
distinct timestamp.

## Triggering a manual backup

If you don't want to wait two hours for the first scheduled backup
to qualify:

```bash
kubectl patch replicationsource -n stateful-demo stateful-demo-data-backup \
  --type=merge -p '{"spec": {"trigger": {"manual": "demo-1"}}}'
```

VolSync sees the new `trigger.manual` value, kicks off a mover Job
immediately. Verify with:

```bash
kubectl get jobs -n stateful-demo -l app.kubernetes.io/created-by=volsync
kubectl logs -n stateful-demo -l job-name=<job-name> -f
```

Once the Job completes, `kopia snapshot list` should show a new
snapshot. Re-running the same `--type=merge` patch with the same
manual-trigger value is a no-op; bump the value (`demo-2`, etc.) to
trigger again.

## Restore-from-backup walkthrough

The magic is here too: delete the PVC, recreate it, watch pvc-plumber
inject the restore handle automatically.

### Step 1 — verify the existing data

```bash
kubectl exec -n stateful-demo deploy/stateful-demo -- wc -l /data/heartbeat.log
# example: 17 /data/heartbeat.log  (17 lines accumulated since pod start)
```

### Step 2 — delete the PVC + Deployment + companion resources

```bash
# Scale the deployment to 0 to release the volume
kubectl scale deployment -n stateful-demo stateful-demo --replicas=0

# Wait for the pod to fully terminate
kubectl wait pod --for=delete -n stateful-demo -l app.kubernetes.io/name=stateful-demo

# Delete the PVC. ArgoCD will recreate it on next sync.
kubectl delete pvc -n stateful-demo stateful-demo-data
```

### Step 3 — let ArgoCD recreate the PVC

```bash
kubectl get application -n argocd app-stateful-demo
# wait for STATUS=Synced after the next reconcile (or trigger:
# argocd app sync app-stateful-demo)
```

When ArgoCD recreates the PVC, pvc-plumber's `validate-pvc` admission
webhook intercepts the create. Three things happen automatically:

1. The webhook calls Kopia (via the operator's in-pod client) and
   asks: "do you have a backup for `stateful-demo/stateful-demo-data`?"
2. Kopia answers yes — and returns the snapshot ID.
3. The `mutate-pvc` admission webhook injects the `dataSourceRef`
   field on the PVC, pointing at the
   `ReplicationDestination/stateful-demo-data-backup` resource. VolSync
   sees this on PVC bind, runs a restore Job, and populates the volume
   from Kopia BEFORE the volume is `Bound` to a pod.

### Step 4 — scale the deployment back up + verify data round-trip

```bash
kubectl scale deployment -n stateful-demo stateful-demo --replicas=1
# wait for pod Running
kubectl exec -n stateful-demo deploy/stateful-demo -- wc -l /data/heartbeat.log
# expected: 17 lines (matches step 1) — PLUS new lines from the
# busybox heartbeat continuing now. The data round-tripped through
# Kopia.
```

This is the contract pvc-plumber's `failurePolicy: Fail` validation
webhook protects: if Kopia can't be reached during a PVC create,
the webhook DENIES the PVC instead of letting it come up empty over
restorable backup data. ArgoCD retries; meanwhile no data loss.

## Common failure modes

- **The three companion resources never appear** — pvc-plumber's
  reconciler is in CrashLoopBackOff. Most common cause: the kopia
  password SealedSecret was never sealed (placeholder still in git).
  `kubectl logs -n volsync-system deploy/pvc-plumber` will show
  "kopia: invalid password" or "secret not found".

- **`ReplicationSource` exists but `lastSyncTime` never populates** —
  either (a) the PVC isn't 2 hours old yet (wait), or (b) the NFS
  export the operator mounts at `/repository` isn't reachable.
  `kubectl exec -n volsync-system deploy/pvc-plumber -- ls -la /repository`
  to check.

- **Restore PVC stuck `Pending` after recreate** — the
  `dataSourceRef` injection didn't fire. Most likely the operator pod
  was down when admission ran (webhook `failurePolicy: Fail` denied
  the create instead). The PVC will retry every ArgoCD sync; bring
  the operator back up and the next retry should succeed.
